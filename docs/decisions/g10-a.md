## The question

CI fetches its TeX package bundle from a third party on every cache miss — do we
keep depending on that host, pin past its redirector, or stop fetching at run time
altogether?

## What is actually there — measured, not assumed

Two facts reframe the problem.

**We use 2% of it.** The 2.88 GB tar is read by ranged request; the working set for
all ten templates is 64 MB. Any plan that moves 2.88 GB around is solving a problem
we do not have.

**There are two hosts, not one.** `relay` is a redirector; `data1b` is storage.
G10's evidence describes 429s on "a moving subset of templates" — the signature of
a rate-limited redirector hit once per document class, not of storage failing. The
exit-101 Rust panic within 350 ms on all ten is a different failure, most likely
the index fetch dying.

## Decision

**Option D — publish the warmed cache, restore it in CI, and seal Tectonic to it —
with option A folded into the same change.**

D is chosen because it is the only option that changes the failure _class_. A, B
and C all leave "CI reaches a third party and might not get an answer" true and
merely make it less likely. D makes it false, using the 64 MB we know is sufficient
rather than the 2.88 GB we do not need.

Three implementation calls, decided here so G10-b does not have to:

1. **The flag reaches Tectonic through a CI-only PATH shim**, not through core.
2. **The cache is warmed by a `workflow_dispatch` job on `ubuntu-latest`**, not on
   a developer's Mac.
3. **The cache lives at a pinned `TECTONIC_CACHE_DIR`**, not at two OS-dependent
   defaults.

### The mechanism

**One pinned cache location.** `TECTONIC_CACHE_DIR` set job-wide, replacing the
two-path `actions/cache` block at `.github/workflows/ci.yml:64-75`.

**Sealed execution, CI only.** A shim written before the test step and placed first
on `$GITHUB_PATH`:

```bash
exec /usr/local/bin/tectonic --only-cached "$@"
```

No recursion: the installer at `ci.yml:80-87` puts the real binary at that absolute
path, and the shim calls it directly. Core spawns `tectonic` by name, so PATH
resolution does the rest.

**Why a shim rather than a flag in core.** The commitment below says local
development stays unchanged and only CI runs sealed. A shim _is_ that statement,
expressed in the layer that owns it. An environment variable read inside core would
say something weaker and more dangerous: that any process anywhere may seal the
renderer, including a developer who exports it once and forgets. Core has zero
`process.env` reads today, and that is deliberate — CLAUDE.md invariant 3 has it
performing no I/O it was not handed. Reading configuration from the ambient
environment is exactly that. The shim keeps G10-b's blast radius inside `.github/`,
which is where a CI policy belongs.

The cost is honest and should be written into the workflow as a comment: a wrapper
on PATH is invisible, and someone debugging a CI-only render failure will lose time
to it unless the file says loudly what it is and why.

**Cache origin.** A `workflow_dispatch` job on `ubuntu-latest` that warms with
`npm ci && npm run build && npm test && npm run qa:all` — both suites, because the
`qa/` harness compiles templates and fixtures the unit tests do not — then tars
`$TECTONIC_CACHE_DIR`, records the tarball's `sha256`, and uploads it as a release
asset named by the bundle digest. Warming on the consumer's own OS removes an
assumption nobody has tested: that a macOS-warmed cache is byte-portable to Linux.
With this job, the question never has to be answered.

**Restore order in the test job.** `actions/cache` keyed on the asset's `sha256`,
with the release download as the cache-miss populate path. The only host CI depends
on is then GitHub, which it already depends on for its source.

**Option A, same PR.** Pin `--bundle` past the redirector — but for the **warm job
only**, since the test job never fetches — and split the bundle cache key off
`hashFiles('packages/core/src/templates/*.ts', 'packages/core/assets/**')`. Today
every template edit invalidates the cache, which is precisely the change most
likely to be under test.

### Checksum strategy — do not invent one

Tectonic already content-addresses the bundle and stores the cache under that
digest, so the strategy is to pin what exists rather than layer something new:

1. Pin `6ffe055852f8faf66c0acbe1a7fb27f87b869a90bad1204f3bf4d9683f597c7c` in
   `ci.yml`, as both the cache key and an asserted value.
2. Record the cache tarball's own `sha256` in the release notes, and verify it after
   download.
3. **Fail the job if the digest Tectonic resolves differs from the pin.** A changed
   digest means upstream re-cut the bundle. That must be a deliberate roll-forward
   with the golden snapshots re-checked — not a silent Tuesday.

The bundle is named `tlextras-2022.0r0` and has not moved since 2022, so pinning
costs nothing in maintenance.

| Option                                                          | Why not                                                                                                                                                                                                                                                                                                                          |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A alone** — pin past the redirector, better cache key         | Removes one of two SPOFs for four lines of YAML, but leaves the failure class intact: a cold cache still reaches a third party. Kept as _part_ of D, not as the answer.                                                                                                                                                          |
| **B** — mirror the whole 2.88 GB bundle                         | Exceeds GitHub Releases' 2 GB per-file limit, so it needs S3/R2 — an account, a bill, a secret, and a new party that can vanish independently. We would be paying to host 2.82 GB we never read. No such host exists for this project.                                                                                           |
| **C** — build a minimal bundle with `tectonic -X bundle create` | Genuinely attractive: a purpose-built ~64 MB bundle is a _supported format_, where D tars a directory layout Tectonic owns privately. | **Core reads an env var** to pass `--only-cached`               | Breaks core's freedom from ambient configuration for a CI-only concern, and makes it trivial to seal a local checkout by accident.                                                                                                                                                                                               |
| **Commit the cache in-tree**                                    | 64 MB of binary blobs in every clone and in history forever, in a repo whose CLAUDE.md already tells readers not to load its 4.5 MB of assets.                                                                                                                                                                                   |

## What this commits us to that is hard to walk back

- **A second artifact to roll forward.** Bumping Tectonic past 0.17.0, or adding a
  template that needs an uncached package, now requires republishing the cache
  asset. That is the real ongoing cost, and it is the reason D beats C _today_:
  D's regeneration is "run the warm job", C's is "author a bundle spec". If that
  ever inverts, so does the recommendation.
- **`--only-cached` changes what a missing package looks like in CI** — a hard
  error instead of a download. That is the intent, but anyone adding a template
  will meet it, so it needs a line in the README and an error message that names
  the warm job as the fix.
- **A PATH shim is indirection.** It is confined to CI and commented, but it is
  still a layer between the workflow and the binary.
- **Local development is deliberately unchanged.** Developers keep the fetching
  behaviour; only CI runs sealed. Making both identical is a larger change than
  this node and would make a first clone worse.
- Nothing here touches the three CLAUDE.md invariants or any caller surface. This
  is entirely a CI-and-cache decision, which is why G10-b is mechanical.

## If we choose wrong, would a test catch it?

**Partly — and the gap is why this was a gate rather than a review.**

_Caught automatically:_ a wrong bundle produces different `.tex` → PDF output, and
`fixtures/golden/` plus the parse-fidelity gates go red. A missing package fails the
build loudly. Both are mechanical.

_Not caught:_ picking a hosting arrangement that works today and rots. If a mirror's
billing lapses, or `data1b` is re-pointed, CI goes red months later with a network
error that looks exactly like the failure being fixed now. No test detects "this
arrangement is fragile" — that is a judgment about durability, which is precisely
what a gate is for.

The decision is shaped around that gap: D depends on GitHub Releases, which the repo
already depends on for its source, so it adds no new party that can disappear on its
own schedule.

## Revisit if

- **Regenerating the cache asset becomes a recurring chore.** Then spend the thirty
  minutes on `tectonic -X bundle create`; a supported bundle format beats a tarred
  private cache layout, and C becomes the better answer.
- **Tectonic moves past 0.17.0.** D tars a directory Tectonic owns. If 0.18
  reorganises it, the published asset is dead. The version pin already guards this,
  and it is the assumption in this record most likely to be wrong.
- **Evidence emerges that the 429s came from `data1b` rather than `relay`.** That
  would make option A's redirector pin worthless and strengthen the case for
  sealing further.

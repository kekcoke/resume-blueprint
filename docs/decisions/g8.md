## The question

G8-a added `tsconfig.test.json` to all five packages and ran the typecheck for real.
It surfaced exactly one error, in one file, at one call site. Is that error in scope
to fix as part of G8-c — the node that also wires the typecheck into `build`/`test`
for good — or does it get deferred?

## What is actually there — measured, not assumed

Read from `qa/findings.md`'s G8-a report, itself generated by
`npm run typecheck:test` on 2026-08-24.

| Fact                              | Value                                                                                                                                                                                                       |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Packages typechecked              | core, store, mcp, cli, http — all 5                                                                                                                                                                         |
| Packages with zero errors         | core, store, mcp, cli                                                                                                                                                                                       |
| Packages with errors              | http — exactly 1                                                                                                                                                                                            |
| The error                         | `test/http.test.ts(126,9): error TS2698: Spread types may only be created from object types.`                                                                                                               |
| Root cause                        | `readFixture()` (`http.test.ts:17`) returns `Promise<unknown>`; every call site passes the result straight to `JSON.stringify` (accepts `unknown`) except line 126, which spreads it into an object literal |
| Other call sites of `readFixture` | lines 100, 121, 334 — all `JSON.stringify(sample)`, none spread, none error                                                                                                                                 |
| Blast radius of a fix             | one file, one type annotation, zero runtime behavior change                                                                                                                                                 |
| Interface touched                 | none — `readFixture` is test-local, not exported, not part of any package's public surface                                                                                                                  |

There is exactly one finding here, not a body of them to triage. The proposed fix
already suggests itself from the shape of the error: `readFixture` doesn't need to
return `unknown` — nothing downstream ever narrows it before use, so the honest type
is a plain JSON object, not an opaque unknown that then requires an unsound spread to
work around.

## Decision

**Fix now, as part of G8-c.** Change `readFixture`'s return type from
`Promise<unknown>` to `Promise<Record<string, unknown>>`. That's an object type, so
the spread at line 126 typechecks without a cast, and every other call site
(`JSON.stringify`) is unaffected since `Record<string, unknown>` is still assignable
there.

**Why not `BlueprintInput` from `@resume-blueprint/core` instead.** `http.test.ts`
loads both `sample.json` (a valid blueprint) and `injection.json` (deliberately
adversarial input exercising the sanitizer — see `CLAUDE.md`'s security posture).
Typing `readFixture` as `Promise<BlueprintInput>` would assert that injection.json
conforms to the blueprint schema, which is not the property that fixture is testing
and may not even be true. `Record<string, unknown>` says only "this is JSON, and
it's an object" — true of both fixtures, and no more than that.

**Why this doesn't need its own gate.** It's a one-line annotation on a test-local
helper, with a concrete failing command already pointing at it
(`npm run typecheck:test --workspace @resume-blueprint/http`). That is a review-shaped
change, not a judgment call — the judgment was only ever "is fixing this in scope",
answered above.

## Options rejected

| Option                               | Why not                                                                                                                                                                                                          |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Defer to a new finding**           | There is nothing to defer — the fix is smaller than the finding-filing overhead, and G8-c's own acceptance test ("every error triaged, not silenced") is satisfied more honestly by fixing it than by filing it. |
| **Suppress with `@ts-expect-error`** | Would be silencing, which is the one outcome G8's original acceptance test explicitly rules out. There is also no reason to silence a fix this cheap.                                                            |
| **Type as `BlueprintInput`**         | Rejected above — asserts a property (`injection.json` is a valid blueprint) that the fixture is not guaranteed, and isn't even meant, to have.                                                                   |

## What this commits us to that is hard to walk back

Nothing. This is a test-local type annotation with no runtime effect, no exported
surface, and no interface anything else depends on. The only real commitment in this
record is process, not code: **G8-c also wires `typecheck:test` into each package's
real `build` or `test` script**, which means every future PR runs it. That is the
change worth naming plainly — a currently-invisible category of bug (type errors in
tests) becomes load-bearing CI surface from here on, the same way G9's `lint` script
made formatting load-bearing.

## If we choose wrong, would a test catch it?

**Yes, immediately, which is exactly why this was small enough to decide in the same
record as the report.** If the fix were wrong — say, too loose to catch a real
mismatch, or too strict and breaking a legitimate call site — `npm run typecheck:test`
itself goes red or green incorrectly, and G8-c's acceptance test
(`npm run build && npm test`, plus the typecheck now wired in) catches it the same
run it's introduced in. There is no silent-failure path here, unlike G2 or G1's gates.

## What G8-c inherits

Mechanical, `sonnet`, review. Acceptance unchanged from the original G8 node:
**typecheck passes over `test/`; every error triaged, not silenced.**

- Change `readFixture`'s return type in `packages/http/test/http.test.ts:17` to
  `Promise<Record<string, unknown>>`.
- Wire `typecheck:test` into each of the 5 packages' real `build` or `test` script
  (not just the standalone root script G8-a added), so it's load-bearing going
  forward rather than a script nobody runs.
- Confirm `npm run build && npm test` still passes at the same test count after
  wiring it in.

## Revisit if

- **A future fixture genuinely needs `readFixture` to return something other than a
  JSON object** (an array, a primitive). `Record<string, unknown>` would then be
  wrong for that one call site, and it should get its own typed overload rather than
  loosening the shared helper back toward `unknown`.
- **The typecheck starts surfacing errors in `build`/`test` regularly enough to slow
  the inner loop.** Then it may be worth a separate fast-path script for local
  iteration, with the full check staying load-bearing in CI.

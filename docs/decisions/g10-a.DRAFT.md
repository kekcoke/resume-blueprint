## The question

CI currently fetches its TeX package bundle from a third party on every cache
miss — do we keep depending on that host, pin past its redirector, or stop
fetching at run time altogether?

## What is actually there — measured, not assumed

Everything below was read off this machine and the live host on 2026-08-24.

| Fact | Value | How it was found |
|---|---|---|
| Bundle Tectonic 0.17.0 asks for | `https://relay.fullyjustified.net/default_bundle_v33.tar` | cache key names in `~/Library/Caches/TectonicProject.Tectonic/bundles/hashes/` |
| What that resolves to | **302** → `https://data1b.fullyjustified.net/tlextras-2022.0r0.tar` | `curl -sSI` |
| Full bundle size | **2,881,562,112 bytes (2.88 GB)** | `content-length` |
| Bundle last modified | **2022-09-25** — frozen, versioned in its own filename | `last-modified` |
| Ranged reads supported | yes (`accept-ranges: bytes`) | response header |
| Content digest Tectonic pins it by | `6ffe055852f8faf66c0acbe1a7fb27f87b869a90bad1204f3bf4d9683f597c7c` | the cache's own hash file |
| Index Tectonic downloads first | 5.1 MB `.index` | cache `data/` listing |
| **What these ten templates actually pull** | **64 MB, 652 files** | `du -sh` on a fully warmed cache |
| `--bundle` accepts | "this URL **or path**" | `tectonic --help` |
| `-C/--only-cached` exists | "Use only resource files cached locally" | `tectonic --help` |
| `tectonic -X bundle create` exists | builds a bundle from a TOML spec | `tectonic -X bundle --help` |

Two facts reframe the problem.

**We use 2% of it.** The 2.88 GB tar is read by ranged request; the working set
for all ten templates is 64 MB. Any plan that moves 2.88 GB around is solving a
problem we do not have.

**There are two hosts, not one.** `relay` is a redirector; `data1b` is storage.
G10's evidence describes 429s on "a moving subset of templates" — that is the
signature of a rate-limited redirector being hit once per document class, not of
storage failing. The exit-101 Rust panic within 350 ms on all ten is a different
failure and more likely the index fetch dying.

## Options

**A. Keep upstream, but pin past the redirector.**
`--bundle https://data1b.fullyjustified.net/tlextras-2022.0r0.tar`, and split the
bundle cache key off `hashFiles(templates, assets)` so a template edit stops
invalidating it.
*Consequence:* removes one of the two SPOFs and the most likely 429 source, for
about four lines of YAML. Still a third-party dependency on a cold cache, and
`data1b` looks like an implementation detail of the relay that upstream may
re-point without notice.

**B. Mirror the whole bundle ourselves.**
*Consequence:* not viable as a GitHub Release asset — 2.88 GB exceeds the 2 GB
per-file limit. Needs S3/R2, which means an account, a bill and a secret. We would
be paying to host 2.82 GB we never read.

**C. Vendor a minimal bundle built with `tectonic -X bundle create`.**
Build a bundle holding only what these templates need, publish it as a release
asset (~64 MB compressed, comfortably under the limit), pass `--bundle`.
*Consequence:* fully self-contained and small. But it puts us in the
bundle-authoring business: the spec TOML is thinly documented, `create` only
emits the `v1` format, and a new template needing one absent `.sty` fails in CI
with a missing-file error rather than downloading it. That failure is *loud*,
which is good, but it makes adding a template a two-step job forever.

**D. Cache the working set and make the network an error.** ← recommended
Publish the warmed 64 MB cache as a release asset keyed by the bundle digest,
restore it into `~/.cache/Tectonic` in CI, and run Tectonic with
`-C/--only-cached`.
*Consequence:* CI never touches the network for TeX at all. A cache miss becomes
an immediate, named error instead of a 2.88 GB refetch. Keeps upstream as the
*source* of the cache without letting it be a *runtime dependency*.

## Recommendation: D, with A as the same-PR fallback

D is recommended because it is the only option that changes the failure *class*.
A, B and C all leave "CI reaches a third party and might not get an answer" true
and merely make it less likely. D makes it false, and it does so with the 64 MB
we already know is sufficient rather than the 2.88 GB we do not need.

**It is verified, not assumed.** On a warm cache:

```
$ tectonic main.tex --outdir . --untrusted --chatter minimal --only-cached
0.37s total → main.pdf
```

Zero network, sub-second. That is the mechanism working.

Do **A** in the same PR regardless, because it is four lines and it is what
repopulates the cache when we deliberately roll it forward.

### Checksum strategy

Do not invent one. Tectonic already content-addresses the bundle by
`6ffe0558…c7c` and stores the cache under that digest, so:

1. Pin `6ffe0558…c7c` in `ci.yml` as the cache key and as an asserted value.
2. Publish the cache tarball with its own `sha256` recorded in the release notes,
   and verify it after download.
3. Fail the job if the digest Tectonic resolves differs from the pinned one. A
   changed digest means upstream re-cut the bundle, and that must be a
   deliberate roll-forward with the golden snapshots re-checked — not a silent
   Tuesday.

The bundle is named `tlextras-2022.0r0` and has not moved since 2022, so pinning
costs nothing in maintenance.

## What this commits us to that is hard to walk back

- **A second artifact to roll forward.** Bumping Tectonic past 0.17.0, or adding
  a template needing an uncached package, now requires republishing the cache
  asset. That is the real ongoing cost, and it is the reason to prefer D over C —
  D's regeneration is "warm the cache and tar it", C's is "author a bundle spec".
- **`--only-cached` in CI changes what a missing package looks like** — a hard
  error instead of a download. That is the intent, but anyone adding a template
  will meet it, so it needs a sentence in the README and a clear error message.
- **Local development is deliberately unchanged.** Developers keep the normal
  fetching behaviour; only CI runs `--only-cached`. Making both identical is a
  bigger change than this node, and it would make a first-time clone worse.
- Nothing here touches the three CLAUDE.md invariants or any caller surface.
  This is entirely a CI-and-cache decision, which is why G10-b is mechanical
  once this is settled.

## If we choose wrong, would a test catch it?

**Partly, and the gap is the reason this is a gate.**

Caught automatically: a wrong bundle produces different `.tex` → PDF output, and
`fixtures/golden/` plus the parse-fidelity gates would go red. A missing package
fails the build loudly. Both are mechanical.

**Not caught:** picking a *hosting* strategy that works today and rots. If we
mirror to a personal S3 bucket and the card expires, or `data1b` gets re-pointed,
CI goes red months later with a network error that looks exactly like the failure
we are fixing now. No test detects "this arrangement is fragile" — that is a
judgment about durability, and it is precisely what A5 says a gate is for.

The recommendation is shaped around that: D depends on GitHub Releases, which the
repo already depends on for its source, so it adds no new party that can go away
independently.

## What would change my mind

- **`bundle create` turning out to be pleasant.** If building a minimal bundle is
  genuinely a one-command job, C is cleaner than D — a purpose-built 64 MB bundle
  beats a tarred cache directory, because it is a supported format rather than an
  internal layout. I have not tried it; the `v1`-only format and undocumented
  spec TOML are what push it to second place. **Worth thirty minutes before
  signing off.**
- **The cache layout being unstable across Tectonic versions.** D tars a directory
  Tectonic owns. If 0.18 reorganises it, the asset is dead. Pinning 0.17.0 already
  guards this, but it is the assumption most likely to be wrong.
- **Evidence that the 429s come from `data1b` rather than `relay`.** That would
  make A worthless and strengthen D further.

# resume-blueprint

Local-first resume service: a validated JSON Resume blueprint in, a typeset PDF out.
Built for local agents (Claude Code, Hermes) and workflows (n8n) to create and update
resume blueprints over time.

**Phase 1 is complete** (core + CLI, 44 tests green). Phase 2 is the store, MCP server,
and HTTP adapter — see `docs/phase-2-plan.md`.

## Commands

```bash
npm run build    # typecheck + emit; builds core before cli (order matters)
npm test         # builds, then runs all tests
npm run test:update-golden --workspace @resume-blueprint/core   # re-baseline .tex snapshots
```

Requires [Tectonic](https://tectonic-typesetting.github.io/) on PATH (`brew install tectonic`).
Its first compile of a template downloads packages and is slow; later ones are sub-second.

## Do not read these into context

- `packages/core/assets/` — 4.5MB of binary fonts and vendored `.cls`/`.sty` files
- `fixtures/golden/` — 44KB of generated `.tex` snapshots, regenerated by the test suite

Neither is human-authored. Reading them wastes context and teaches you nothing.

## Invariants

These are load-bearing. Both are subtle, both are easy to break, and breaking either is
hard to notice.

### 1. Store raw blueprints. Sanitize only at render time.

`sanitizeBlueprint` escapes LaTeX specials (`&` → `\&`, `\` → `\textbackslash{}`) and is
**not idempotent**. If sanitized output is ever written back to storage, the next
edit-and-render cycle escapes it again: `R&D` → `R\&D` → `R\textbackslash{}\&D`. User data
corrodes slightly on every edit.

Persisted blueprints hold raw user text. `blueprintToTex` and `renderBlueprint` sanitize on
the way to the engine and never write back.

### 2. The MCP server never writes to stdout, and never returns PDF bytes.

stdout **is** the JSON-RPC transport — one stray `console.log` corrupts the stream and
fails confusingly. All diagnostics go to stderr.

PDFs are returned as `{ path, pageCount, byteSize }`. A 24KB PDF is ~32K characters of
base64, spent conveying a document the agent cannot read.

### 3. Core stays free of adapter and UI concerns.

`packages/core` knows nothing about MCP, HTTP, or argv, and performs no I/O it was not
handed. Every interface is a thin adapter over the same call path. Core's runtime
dependencies are `zod` and `common-tags` — adding another needs a real justification.

## Conventions

- ESM + TypeScript, NodeNext resolution: **relative imports need explicit `.js` extensions**
- Tests live in `packages/*/test/` and import from `../dist/`, not `../src/` — Node's type
  stripping does not remap `.js` specifiers to `.ts`, and this exercises what ships
- Conventional commits (`feat:`, `fix:`, `test:`, `docs:`, `chore:`). Commit messages
  explain *why*; they are the primary way context survives between sessions
- Prettier style: no semicolons, single quotes, no trailing commas

## Where the context lives

This project was built across sessions, so rationale is deliberately durable:

- **`git log`** — commit messages carry the reasoning for non-obvious decisions
- **Source comments** — e.g. why `template9` uses `700bp` not `700px`, why template7's
  vendored moderncv is deliberately unstaged
- **`README.md`** — setup, security model, and known gaps
- **`docs/phase-2-plan.md`** — Phase 2 scope, TDD sequences, and validation gates

Prefer these over re-deriving from source. If something looks arbitrary, `git log -S` the
line before changing it.

## Security posture

Blueprint content may be LLM-written or scraped, and is interpolated into a document
handed to a TeX engine — a programming language. Two layers:

1. `packages/core/src/sanitize.ts` escapes LaTeX specials in a single pass
2. The renderer invokes Tectonic with `--untrusted`, disabling shell-escape

`fixtures/injection.json` exercises both. Any new surface that accepts blueprints must
route through the same sanitize path and be tested against that fixture.
